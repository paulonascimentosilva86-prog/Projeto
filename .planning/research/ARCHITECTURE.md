# Testing and Validation Architecture — Claude Code Legal Ecosystem

**Date:** 2026-03-28
**Scope:** 48 slash commands, 6 agents, 5 calculators, 2 Bash hooks, Remotion components

---

## 1. Component Boundaries: What Tests What

The ecosystem has four distinct component types with fundamentally different testability profiles. Each requires a different testing strategy because they fail in different ways.

### 1.1 Calculators (5 components — highest priority)

**Components:**
- `calculadora-condominial.md` — debt sheet: principal + multa 2% + juros 1%/month + INPC + fees 30%
- `calculadora-distrato.md` — real estate rescission: 25%/50% retention + fruition fee (Lei 13.786/2018)
- `calculadora-aluguel.md` — rent adjustment by index (IGP-M, IPCA, INPC)
- `insalubridade-periculosidade.md` — hazard pay + ripple effects across all labor entitlements
- `simulador-reclamatoria.md` — full labor claim projection in 3 scenarios (optimistic / realistic / settlement)

**What can go wrong:** Wrong formula, wrong legal rate, wrong ripple-effect chain, wrong base (salary vs. minimum wage), wrong index application.

**What tests what:**
- **Unit tests** (deterministic): Fixed inputs → expected numeric output. No model inference needed. A Python/Bash script with known values verifies the formula logic embedded in the prompt.
- **Snapshot tests**: Canonical output format (table column headers, row order, summary block) must remain stable across prompt edits.
- **Boundary tests**: Zero months, single competency, maximum hazard grade, all ripple effects combined.

**Test owner:** `tests/calculadoras/` — fully automated, no LLM call required. The formulas are explicit in the Markdown; they can be re-implemented in a reference calculator and outputs compared.

### 1.2 Bash Hooks (2 components — medium priority)

**Components:**
- `hooks/validar-peticao.sh` — checks for mandatory structural elements via `grep -qi`; exits 0 always (warning-only today)
- `hooks/backup-documento.sh` — creates timestamped copy in `.backups/`

**What can go wrong:** Silent miss of a mandatory element, false positive on partial match, backup overwrite on same-second call, no-op on missing file path.

**What tests what:**
- **Shell unit tests** (Bash/bats): Provide fixture documents (complete and intentionally broken) and assert correct ALERTA output and exit code.
- **Blocking behavior test**: Once hooks are upgraded to `exit 1` on failure, assert that a petition missing "dos pedidos" blocks generation.
- **Backup idempotency test**: Call twice within the same second; both copies must exist.

**Test owner:** `tests/hooks/` — fully automated Bash tests, no LLM needed.

### 1.3 Slash Commands — Petition Generators (43 commands)

**Components:** All `.md` files in `.claude/commands/` that generate legal documents (`peticao-trabalhista`, `acao-despejo`, `divorcio`, `usucapiao`, etc.)

**What can go wrong:** Missing mandatory section (endereçamento, qualificação, fatos, direito, pedidos), wrong legal foundation cited, missing OAB / date / valor da causa, tribunal-incompatible format.

**What tests what:**
These are prompts, not functions. The output is natural language generated by an LLM. There is no deterministic unit test. Instead:

- **Structural snapshot tests**: Run the command with a canonical fixture input via `claude -p` (Claude Code headless mode). Parse the output for required section headers using the same `grep` logic as `validar-peticao.sh`. Assert presence of all sections.
- **Legal baseline checklist**: For each command, define a minimum set of legal references that must appear (e.g., `peticao-trabalhista` must cite CLT art. 7o CF/88 and at least one TST súmula). Automated grep-based assertion.
- **Format compliance**: Assert Portuguese date format (DD/MM/AAAA), monetary values with two decimal places, numbered pedidos list.

**Test owner:** `tests/commands/` — uses fixture `.txt` files as input and shell scripts to validate output. Each command gets one canonical test case and one edge case (e.g., rescisão indireta, partial data).

**Important constraint:** These tests require an actual Claude Code invocation. They are integration tests, not unit tests. They should run in CI with rate limiting, not on every file change. See Section 4 for data flow.

### 1.4 Agents (6 components)

**Components:** `agentes/trabalhista/`, `agentes/civel/`, `agentes/condominial/`, `agentes/imobiliario/`, `agentes/familia/`, `agentes/produtividade/`

**What can go wrong:** Agent uses outdated legal reference (wrong CLT article, repealed súmula), agent recommends wrong procedure for the case type, agent forgets to ask which polo the client occupies.

**What tests what:**
- **Schema validation**: Assert that each `AGENT.md` contains required sections (Identidade, Areas de Atuacao, Base Legal Principal, Diretrizes, Comandos Relacionados). Automated Markdown structure check.
- **Legal reference linting**: Parse the `Base Legal Principal` and `Diretrizes` sections. Assert that referenced laws exist in a curated whitelist (CLT 13.467/2017, CF/88 art. 7o, Lei 13.786/2018, etc.).
- **Cross-reference consistency**: Each agent's `Comandos Relacionados` list must point to existing command files. Automated file existence check.

**Test owner:** `tests/agentes/` — entirely automated, no LLM call needed.

### 1.5 Remotion Video Components

**Components:** `remotion-videos/src/` — React/TypeScript compositions for legal marketing videos.

**What can go wrong:** TypeScript compilation failure, broken component props, missing asset references.

**What tests what:**
- **TypeScript build check**: `npx tsc --noEmit` in CI.
- **Remotion render smoke test**: `npx remotion render` on one composition with minimal props to assert no runtime crash.

**Test owner:** `tests/remotion/` or inline via `package.json` scripts.

## 3. How Tests Interact with Claude Code Commands

Commands are Markdown prompt files, not executable functions. This shapes every design decision.

### 3.1 The Headless Invocation Pattern

Claude Code supports headless execution via:

```bash
claude -p "$(cat tests/commands/fixtures/peticao-trabalhista-case1.txt)" \
       --command /peticao-trabalhista \
       > /tmp/output-peticao-trabalhista.txt
```

The test runner pipes a fixture input through the command and captures the generated document. Validation happens entirely on the output file — no inspection of model internals.

### 3.2 What "Testing a Command" Actually Means

A command test does not assert that the output is legally perfect (the model's legal knowledge is not testable in CI). It asserts:

1. **Structural completeness**: All mandatory sections are present (same logic as `validar-peticao.sh`).
2. **Format compliance**: Date format, monetary notation, numbered list structure.
3. **Legal anchor presence**: At minimum, the command's core legal citations appear somewhere in the output.
4. **No hallucinated section removal**: The prompt defines a required structure; the output must reflect it.

### 3.3 Test Contract Per Command

Each command in `tests/commands/expected-elements/` has a JSON contract:

```json
{
  "command": "peticao-trabalhista",
  "required_sections": ["Enderecamento", "Qualificacao", "Dos Fatos", "Do Direito", "Dos Pedidos", "Valor da Causa"],
  "required_legal_refs": ["CLT", "CF/88", "TST"],
  "format_checks": ["R\\$ [0-9]+,[0-9]{2}", "\\d{2}/\\d{2}/\\d{4}"],
  "forbidden_patterns": ["PLACEHOLDER", "\\[inserir\\]", "\\[NOME\\]"]
}
```

The generic `validate-output.sh` reads this contract and runs each check with `grep -qiE`.

### 3.4 Prompt-as-Test vs. LLM-as-Oracle

There is a temptation to use Claude itself to judge output quality ("does this petition look correct?"). This creates a circular dependency and is not deterministic. The architecture deliberately avoids LLM-as-oracle for the testing layer. All assertions are text pattern matches, reducing flakiness and eliminating recursive API costs.

### 3.5 Calculator Commands as a Special Case

The 5 calculator commands are prompts that contain explicit formulas. For these, the test strategy is hybrid:
- **Offline formula test**: Re-implement the formula in Python (extracted from the Markdown) and assert expected values. This is the primary test — fast, deterministic, no API call.
- **Snapshot test**: Run the command once, save the output as a golden file. On subsequent runs, diff the table structure (not the values, since those change with INPC). Alert on structural drift.

## 4. Data Flow for Validation

```
INPUT FIXTURE
(plain text, structured or free-form)
        |
        v
[FIXTURE LOADER]
test-suite-commands.sh reads fixture file
        |
        v
[COMMAND INVOCATION]
claude -p "$(fixture)" --command /COMMAND_NAME
        |
        v
[RAW OUTPUT]
Generated document in /tmp/output-{command}-{case}.txt
        |
        v
[STRUCTURAL VALIDATOR]               [FORMULA VALIDATOR — calculadoras only]
validate-output.sh reads              Python/Bash re-implements formula
expected-elements/{command}.json      Compares with known expected values
        |                                       |
        v                                       v
[GREP ASSERTIONS]                    [NUMERIC DIFF]
required_sections present?           |output_value - expected| < epsilon
required_legal_refs present?
format_checks match?
forbidden_patterns absent?
        |
        v
[HOOK VALIDATION — if file saved]
validar-peticao.sh runs on output
        |
        v
[RESULT AGGREGATOR]
PASS / FAIL with element-level detail
Exit code 0 = all pass, 1 = any fail
        |
        v
[BACKUP]
backup-documento.sh archives output
(test artifacts preserved in tests/outputs/.backups/)
```

**No database is required at any step.** Each test run is self-contained. Fixtures are static files; outputs are ephemeral temp files. The only state that persists is the golden snapshot files in `tests/commands/snapshots/` (updated intentionally, not automatically).

**Rate limiting:** Command tests (which require LLM calls) must be gated. Recommended: run calculator tests and hook tests on every commit; run command tests only on pull requests or scheduled nightly runs.

## 5. Suggested Build Order

Priority is determined by: (1) risk of real harm from failure, (2) testability without LLM, (3) dependency between layers.

### Wave 1 — Zero-Dependency Foundation (build first, no LLM needed)

**1a. Hook unit tests** (`tests/hooks/`)
- Why first: `validar-peticao.sh` is already the closest thing to a test harness. Make it reliably testable before everything else depends on it.
- Deliverable: Fixture documents (complete + broken petitions), `test-validar-peticao.sh` using bats or plain Bash asserts.
- Time estimate: Half a day.

**1b. Agent schema validator** (`tests/agentes/`)
- Why second: Pure static analysis, no API cost, immediate signal on structural regressions.
- Deliverable: `test-agent-schema.sh` that asserts all 6 AGENT.md files have required sections and all cross-referenced command files exist.
- Time estimate: 2 hours.

### Wave 2 — Calculator Accuracy (highest legal risk)

**2a. Formula reference implementations** (`tests/calculadoras/`)
- Why before LLM tests: A calculation error is objectively wrong. This layer catches bugs without needing the model. Start with `calculadora-condominial` (most used, most complex formula chain).
- Build order within calculators:
  1. `calculadora-condominial` — multa 2% + juros 1%/month + INPC chain + 30% fees
  2. `insalubridade-periculosidade` — ripple effects are the hardest to get right
  3. `simulador-reclamatoria` — depends on insalubridade formulas
  4. `calculadora-distrato` — Lei 13.786/2018 branching logic
  5. `calculadora-aluguel` — straightforward index application
- Deliverable: Python scripts with `pytest` or Bash scripts with `bc` arithmetic, fixture JSON files, expected output JSON files.
- Time estimate: 2–3 days.

### Wave 3 — Hook Upgrade (blocking validation)

**3a. Upgrade `validar-peticao.sh` to blocking mode**
- Change `exit 0` to `exit 1` when `ERRORS > 0`.
- The Wave 1 tests must already pass before this change is made — they serve as the safety net proving the hook is correct before it becomes blocking.
- Add granular checks: valor da causa, OAB number, date, pedidos numbered list.
- Time estimate: 1 day.

### Wave 4 — Command Structural Tests (LLM integration)

**4a. Core commands first** (highest-frequency + highest-stakes):
1. `/peticao-trabalhista` — most generated document type
2. `/execucao-condominial` — core office specialty
3. `/defesa-trabalhista` — counterpart to peticao
4. `/acao-despejo` — high volume
5. `/calculadora-condominial` (LLM snapshot, formula already covered in Wave 2)

**4b. Expand to remaining 43 commands**
- Use the generic `run-command-test.sh` + contract JSON pattern.
- One fixture + one contract per command. Parallelize where API limits allow.
- Time estimate: 3–5 days (mostly fixture authoring time).

### Wave 5 — Remotion Build Validation

**5a. TypeScript compilation + render smoke test**
- Lower legal risk than petition generators; build last.
- Integrate into CI as a separate job: `npm run build --prefix remotion-videos`.
- Time estimate: Half a day.

### Wave 6 — Continuous Validation (ongoing)

**6a. Legal reference linting**
- Maintain `legal-refs-whitelist.txt` with current valid citations.
- Run on every commit against all 48 command files and 6 agent files.
- Flag when a command references a law/súmula not in the whitelist (could be outdated or typo).

**6b. Snapshot drift detection**
- Monthly: re-run all command tests and diff structural output against golden snapshots.
- Non-deterministic content will differ; structural sections must not.

## Key Architectural Decisions

| Decision | Rationale |
|---|---|
| No LLM-as-oracle | Circular dependency, non-deterministic, API cost. All assertions are text patterns. |
| Formulas re-implemented in Python/Bash (not tested via model output) | Calculator bugs are objectively verifiable without inference. |
| Hooks upgraded to `exit 1` only after unit tests pass | Prevents false positives from blocking all document generation. |
| One contract JSON per command | Decouples validation logic from fixture content. New test cases reuse the same contract. |
| Calculator tests in Wave 2, before command LLM tests | The formula is the ground truth. LLM output tests for calculators only test table structure, not math. |
| Static fixture files, not generated inputs | Reproducibility. A test that generates its own input via LLM is not a test. |

## What This Architecture Does Not Cover

- **Semantic legal quality**: Whether the legal argument is strong or the petition would succeed in court. This requires domain expert review, not automation.
- **Index value accuracy** (INPC, IGP-M, IPCA): Tests use fixed known index values from a specific date. Real-time index fetching is out of scope for automated tests.
- **Tribunal-specific formatting variations**: Each TRT has formatting preferences. Tests assert minimum ABNT compliance, not full tribunal-specific compliance.
- **Multi-turn agent conversations**: Agent behavior across a full back-and-forth session is not tested. Only the agent's AGENT.md schema and cross-references are validated statically.
